## What this is

icsmoi is an Avalonia (.NET 10) system for building and running force-feedback (FFB) profiles for flight simulators (MSFS2020/2024). Users wire together a node graph — SimConnect telemetry inputs, math/logic/curve nodes, FFB effect outputs — on a visual canvas, and an evaluation engine runs that graph in real time to drive real force-feedback hardware.

There is no README; this project is being built in phases (see commit history and `Docs`-free in-code phase comments). A detailed implementation plan for the current body of work (real SimConnect telemetry, real DirectInput FFB output, new node types, shared visual design) lives at `C:\Users\crist\.claude\plans\msfs2020-and-msfs2024-do-golden-meerkat.md` — read it before starting work on any phase beyond 4, since it records the reasoning behind decisions below, not just the "what."

## Solution structure

Four projects under `/src`, referenced from `icsmoi.slnx`:

- **`icsmoi.Core`** (class library) — `Models/`, `Engine/`, `Services/`. All graph/profile/evaluation logic and (from Phase 5 onward) the SimConnect telemetry client and DirectInput hardware-output services. References `Avalonia` (base only, not `Avalonia.Desktop`) and `NodifyM.Avalonia` directly on the node/pin model types (`NodeViewModel : INodePosition`, `PinViewModel : ConnectorViewModelBase`) — this is a deliberate, accepted trade-off: `icsmoi.Runtime` inherits an unused `NodifyM.Avalonia.dll` in its output folder (inert disk weight, never instantiated/rendered) rather than the larger refactor of introducing plain DTOs + an Editor-side translation layer. Do not "clean this up" unprompted.
- **`icsmoi.Editor`** (WinExe) — the node-graph authoring app (`Views/`, `ViewModels/`, `ViewLocator.cs`, `App.axaml`). NodifyM.Avalonia-dependent canvas UI. **Never acquires real FFB hardware** — it only shows simulated magnitude/parameter readouts (the `LastMagnitude`-style pattern) while authoring. Real telemetry ("Connect to Sim" toggle, from Phase 5) and read-only joystick input (Joystick Input node, polled while the engine runs) are fine here; real DirectInput hardware *output* is not.
- **`icsmoi.Runtime`** (WinExe) — the lightweight background app: tray icon + a small status window (`Views/StatusWindow.axaml` + `ViewModels/StatusWindowViewModel.cs`), loads a saved profile and actually drives telemetry + FFB hardware. No `NodifyM.Avalonia` reference in its own code (only inherited transitively via Core, per above) — never render a graph canvas here. This is the *only* app that wires up `FfbEffectManager` to `FfbEngineService.HardwareOutputsUpdated`, and only once the user explicitly opts in — see the "Effects safety gate" note below.
- **`icsmoi.Shared.Ui`** (resource-only class library) — shared Avalonia design tokens (`Styles/Tokens.axaml`), merged into both exe projects' `App.axaml` so they present a consistent look despite being separate processes — see "Visual design system" below.

Namespaces were left as `icsmoi.Models`/`icsmoi.Engine`/`icsmoi.Services`/`icsmoi.ViewModels`/`icsmoi.Views` regardless of which project a file lives in — they don't need to match assembly names, and keeping them unchanged avoided a mechanical rename across every file during the project split.

## Architecture

### Node graph editor (NodifyM.Avalonia)

The canvas is built on the `NodifyM.Avalonia` library. `MainWindowViewModel` (in `icsmoi.Editor`) derives from `NodifyEditorViewModelBase`, which supplies the `Nodes`/`Connections` collections and drag/connect gestures used directly by the XAML in `Views/MainWindow.axaml`.

There are **two parallel representations of the graph** that must be kept in sync manually:
- `MainWindowViewModel.Nodes` / `.Connections` — the live UI-facing collections NodifyEditor renders and manipulates.
- `MainWindowViewModel.Profile` (an `FfbProfile`) — the serializable model (`Profile.Nodes` / `Profile.Connections`), persisted to disk.

Every mutation (add node, connect, disconnect, delete, load) touches both sides. See `Connect`, `DisconnectConnector`, `DeleteSelection`, and `LoadProfile` in `src/icsmoi.Editor/ViewModels/MainWindowViewModel.cs` — when adding new graph-mutating operations, follow this same dual-update pattern rather than assuming one collection drives the other.

### Node model (icsmoi.Core/Models/)

`NodeViewModel` is the abstract base (`Id`, `X`/`Y`, `Inputs`/`Outputs` pin collections). Concrete node types:
- `SimConnectNodeViewModel` — one output pin, reads a named variable from sim data.
- `JoystickInputNodeViewModel` (`DeviceInstanceGuid` + a variable number of `JoystickPinViewModel` outputs) — reads any DirectInput game controller (force feedback not required). Each output pin is one binding: `Kind` (`Axis`/`Button`) + `Index` (a `JoystickAxis` ordinal — X/Y/Z, three rotations, two sliders — or the zero-based button number; shown 1-based as "Button 3"). Axes output [-1, 1] (0 at centre — use a Range Map/Math node for 0..1), buttons output 1.0/0.0. `JoystickPinViewModel` is a `PinViewModel` subclass registered with `[JsonDerivedType]` on `PinViewModel`; plain pins still serialize without a type tag, so existing profiles load unchanged. Its binding lives on the pin (not a parallel list on the node) so each row lays out beside its own connector. Live values arrive via `JoystickInputService` — see "Joystick input" below. Unassigned pins, or a node with no device, read 0.
- `MathNodeViewModel` — two input pins (`A`, `B`), one output; evaluates an NCalc `Expression` string (e.g. `[A] + [B]`) where pin `Title`s become NCalc parameter names.
- `ConstantForceOutputNodeViewModel` (`Magnitude` → real DirectInput Constant Force), `ConditionOutputNodeViewModel` (`PositiveCoefficient`,`NegativeCoefficient`,`Offset`,`DeadBand`,`Saturation` → real DirectInput Spring/Damper/Inertia/Friction, picked via a `ConditionKind` property), `PeriodicOutputNodeViewModel` (`Magnitude`,`Period`,`Phase`,`Offset` → real Sine/Square/Triangle/SawtoothUp/SawtoothDown, picked via a `Waveform` property — there is no single "Periodic" DirectInput effect GUID, each waveform is its own GUID), `RampForceOutputNodeViewModel` (`StartMagnitude`,`EndMagnitude`,`Duration` → real DirectInput Ramp Force, the one hardware-output node whose `Duration` is finite rather than "play until stopped"). All four derive from the abstract `HardwareOutputNodeViewModel` (which carries `DeviceInstanceGuid`/`AxisIndex`/`DirectionDegrees`/`Gain` for hardware targeting, so the Editor renders one shared settings block for them). `AxisIndex` is an index into the device's force axes ordered by HID usage (X, then Y) or `AllAxes` (-1, the default for new nodes; old profiles keep their saved index); `DirectionDegrees` (0° = forward/away from the pilot, clockwise) only matters for `AllAxes` and only for effects where `SupportsDirection` is true — constant/periodic/ramp; **Condition nodes are per-axis (the same condition on every axis, like the sibling TDX spring), so `ConditionOutputNodeViewModel.SupportsDirection` is false and the Editor shows no dial for them** and each has a `[JsonIgnore]` live readout. Their input pins are also editable in the Editor — see the `PinViewModel.Value` note below.
- `ComparisonNodeViewModel` (`A`,`B` → `Result`, `Operator` enum `>`/`<`/`>=`/`<=`/`==`/`!=`), `LogicNodeViewModel` (`A`,`B` → `Result`, `Operator` enum AND/OR/NOT/XOR — `B` stays present but unused for NOT rather than being dynamically hidden), `SelectNodeViewModel` (`Condition`,`IfTrue`,`IfFalse` → `Result`) — all keep the graph's all-`double` wire convention (nonzero = true, 1.0/0.0 out) rather than introducing a separate bool pin type.
- `ClampNodeViewModel` (`Value`,`Min`,`Max` → `Result`), `RangeMapNodeViewModel` (`Value`,`InMin`,`InMax`,`OutMin`,`OutMax` → `Result`, plus a `Clamp` bool property), `CurveNodeViewModel` (`Value` → `Result`, backed by an `ObservableCollection<CurvePoint>` piecewise-linear curve) — the general-purpose way to express a telemetry-to-effect formula (e.g. an airspeed-to-stiffness curve) visually instead of hardcoding it in C#. The Curve node's control points are edited via `Views/CurveEditorControl.cs`, a fully custom-rendered Avalonia `Control` (no XAML template) embedded directly in its `DataTemplate` — double-click empty space to add a point, double-click a point to remove it, drag to reshape. Its view bounds are fit to the point set once on attach/collection-change, not recomputed every render, so dragging a point doesn't make the view rescale out from under the pointer.

`PinViewModel` wraps `NodifyM.Avalonia`'s `ConnectorViewModelBase`; `IsInput` is set once via `init` and mirrors the `Flow` enum. `Anchor` (screen position) is `[JsonIgnore]` — runtime-only, never persisted.

**Pin constants (`PinViewModel.Value`).** Every input pin carries a persisted `double Value` — the constant used while nothing is wired into it, so a hardware-output parameter no longer needs a dedicated Math node just to hold a number. `GraphEvaluator` seeds every *input* pin's wire value with `pin.Value` (outputs start at 0), and a connected pin's value is simply overwritten when its source node propagates — the evaluator never consults `IsConnected`, only the connection list, so it stays valid for every node type (Value defaults to 0, so nodes/profiles that never set it behave exactly as before; an old profile with no `Value` in its pins loads as 0). Every node template with input pins (Compare, Logic, Select, Clamp, Range Map, Curve and the four hardware outputs) *shows* a field (via `ValueInputPinTemplate` — see "Visual design system") — **except Math Compute**, which deliberately uses the plain `InputPinTemplate`: its constants belong in the expression (`[A] + 2`), so a field there was redundant (its pins' `Value` stays 0 and nothing can set it); new-node defaults that matter beyond the hardware ones: Clamp `Min`/`Max` −1/1, Range Map an identity 0..1 → 0..1, Select `IfTrue` 1. Because pins are restored from JSON rather than rebuilt by the node constructor, per-pin metadata (default, min/max) can't live on the pin without being lost on load; the constructor's `Value = …` initializers (e.g. Condition `Saturation` 1.0, Periodic `Period` 0.1 s — a zero period isn't a valid DirectInput periodic effect — Ramp `Duration` 1.0 s) only apply to *newly created* nodes. `MainWindowViewModel.LoadProfile` resets every pin's persisted `IsConnected` to false before re-marking connected pins from the connection list, since the field's visibility depends on that flag.

Adding a new node type means: create a `NodeViewModel` subclass with its pins wired up in the constructor, register it with `[JsonDerivedType(...)]` on `NodeViewModel`, add a case to `GraphEvaluator.Evaluate`'s switch, and add an `Add<X>Node` command + palette entry in `MainWindowViewModel`/`MainWindow.axaml` (Editor only — Runtime never adds nodes, it only loads/runs saved profiles). For a node with fixed-name input pins and a single output (i.e. everything except `MathNodeViewModel`, which maps *all* its inputs generically into NCalc parameters), reuse `GraphEvaluator`'s `GetPinValue(node, title, wireValues)`/`SetOutputValue(node, value, wireValues)` helpers rather than re-deriving pin lookup.

### Evaluation engine (icsmoi.Core/Engine/)

`GraphEvaluator` is a stateless, pure evaluator: given a snapshot of nodes/connections plus a `simData` dictionary, it topologically sorts the graph with Kahn's algorithm (returning `null` if a cycle is detected — the engine skips that tick rather than throwing), then evaluates nodes in dependency order, propagating values through a `pin ID → value` map after each node runs.

`FfbEngineService` drives this on a `System.Threading.Timer` (default 10ms / 100Hz). Key points:
- The graph snapshot is held in a `volatile` field, swapped atomically via `RefreshSnapshot` whenever the profile's nodes/connections change — the timer thread never sees a torn/partial graph.
- `SimData` is a `ConcurrentDictionary` — from Phase 5 onward, `SimConnectTelemetryService` writes into it continuously from its own background thread.
- **`OutputsUpdated` fires on the timer thread itself, not the UI thread** — `FfbEngineService` has no Avalonia-UI-thread dependency by design, since it's shared between the Editor and the headless Runtime app. Each host marshals to its own UI thread in its own subscriber (see `MainWindowViewModel.OnEngineOutputsUpdated`'s `Dispatcher.UIThread.Post` wrapper in the Editor). Don't reintroduce a `Dispatcher` call inside `FfbEngineService` itself.
- **`HardwareOutputsUpdated`** fires alongside `OutputsUpdated` on the same tick, carrying `IReadOnlyDictionary<Guid, EffectOutputParams>` — richer per-effect-type parameters (e.g. a Condition node's 5 coefficients) that a single scalar magnitude can't express. Only `icsmoi.Runtime`'s `FfbEffectManager` is meant to subscribe to this (not yet wired — that's Phase 8); the Editor only ever consumes `OutputsUpdated`.

`GraphEvaluator.Evaluate` returns `NodeOutputResult(Magnitudes, EffectParams)` rather than a bare dictionary — `Magnitudes` is populated for every hardware-output node for UI readouts, while `EffectParams` is populated only for node types that actually drive hardware (currently `ConstantForceOutputNodeViewModel`, `ConditionOutputNodeViewModel`).

When editing the graph while the engine is running, call `Engine.RefreshSnapshot(Profile)` — the engine won't otherwise see topology changes until the next explicit refresh.

### DirectInput hardware output (icsmoi.Core/Services/DirectInput/)

`FfbDeviceManager` wraps one `Vortice.DirectInput.IDirectInput8`. `EnumerateDevices()` is safe to call from the Editor (read-only, used to populate the device picker's dropdown) — `AcquireDevice`/effect creation is Runtime-exclusive per the hardware boundary above. Each device's force axes (`FfbAxis`: name, data-format offset, HID usage) are discovered once — by `FfbDeviceManager.DiscoverAxes`, also used by `EnumerateDevices` so the Editor's axis dropdown and the Runtime agree on order — and cached at acquisition, rather than re-queried by every effect (a deliberate fix versus TDX-Air-Mechanics, where every effect class re-ran axis discovery independently). `EnumerateDevices` only *creates* each device object to read its object list (no cooperative level, no `Acquire`, no effect), which is why it stays Editor-safe.

`FfbEffectManager` keeps one long-lived `IDirectInputEffect` per hardware-output node (keyed by node `Id`), created once via `device.CreateEffect(...)` and updated in place via `effect.SetParameters(params, EffectParameterFlags.TypeSpecificParameters | EffectParameterFlags.Start)` — **`Start` is required** (see "Effect update cost" below) but **only sent when something actually changed** (it remembers the last-sent values in DirectInput units per node, `EffectState.Key`), never recreated per tick.

**Vortice.DirectInput API notes** (discovered by reflecting the installed package — its exact shape isn't obvious from SharpDX-parity claims alone):
- No bare `Effect` class — effect handles are `IDirectInputEffect`, created via `IDirectInputDevice8.CreateEffect(Guid, EffectParameters)`.
- `EffectParameters.Parameters` is typed `TypeSpecificParameters`, an abstract base class — the concrete types you actually construct are its public subclasses `ConstantForce` (`Magnitude` int), `ConditionSet` (`Conditions` — a `Condition[]`, one struct per axis, each with `Offset`/`PositiveCoefficient`/`NegativeCoefficient`/`PositiveSaturation`/`NegativeSaturation`/`DeadBand` int fields), `PeriodicForce` (`Magnitude`/`Offset`/`Phase`/`Period` int properties), `RampForce` (`Start`/`End` int properties), `CustomForce` (unused so far). There is **no** separate `Conditions` property on `EffectParameters` itself — assign the `ConditionSet` (or any of the others) through `.Parameters` like any other effect type.
- `EffectParameters.Gain` (not `ForceFeedbackGain`), `.Flags`, `.Duration` etc. are plain fields, not properties.
- **`EffectParameters.Duration` must be set inside each `Build*` method, not centrally in `FfbEffectManager.TryUpdate`** — continuous effects (ConstantForce/Condition/Periodic) use `InfiniteDuration` ("play until stopped"), but Ramp Force needs its own finite duration. An earlier draft set `Duration = int.MaxValue` unconditionally after calling the builder, silently stomping Ramp's real duration — if you add a new effect type, decide its duration inside its own `Build*` method.
- Device acquisition uses `CooperativeLevel` (not `CooperativeLevelFlags`) for `SetCooperativeLevel`'s flags argument.
- All ±10000-range DirectInput integer units are produced by `FfbEffectManager.ToDirectInputUnits(double)` from the graph's normalized `[-1, 1]`-ish doubles — keep new effect types going through this same helper rather than hand-rolling the scaling. `Period`/`Duration` (seconds → microseconds) and `Phase` (normalized `[0,1)` cycle → hundredths-of-a-degree) have their own dedicated helpers for the same reason.
- Verified against real hardware: `FfbDeviceManager.EnumerateDevices()` correctly detects an attached FFB device (product name + instance GUID) with zero acquisition. `AcquireDevice`/`CreateEffect` have not yet been exercised against real hardware in this repo — deliberately: the "Effects" safety gate below has been kept off throughout development. Probing the real TDX Force *without* acquiring it (and a non-FFB device non-exclusively) did establish things that the original code got wrong and that are now fixed — each would have made the Effects toggle silently do nothing or crash. (Effect creation/start/in-place update have since been exercised on the real TDX Force with brief ~8% pushes, with MSFS 2024 running — exclusive acquisition still succeeds alongside it.)
  - **`EffectParameters.TriggerButton` must be set to `-1` (DIEB_NOTRIGGER)**: it defaults to 0, which with `ObjectOffsets` names offset 0 — the Y *axis* — as the trigger button, and `CreateEffect` throws `DIERR_INVALIDPARAM` (0x80070057). **Every effect type/axis choice failed until this was set** (verified by creating variants without starting them: only `TriggerButton = -1` differed between accepted and rejected). `FfbEffectManager.NoTriggerButton`.
  - **`Acquire()` fails (`0x80070057`) unless `SetDataFormat<RawJoystickState>()` is called first** (the `Joystick` class the sibling TDX projects use sets it implicitly; raw `CreateDevice` does not). `AcquireDevice` now sets it and `.CheckError()`s each step (the calls return a `Result` rather than throwing, so an ignored failure used to surface later as an exception from `CreateEffect`).
  - **`GetObjects(DeviceObjectTypeFlags.ForceFeedbackActuator)` returns nothing for the TDX Force** — so the old axis list was empty and every effect was skipped. The axes are found by taking `GetObjects(Axis)` and keeping those whose `ObjectId.Flags` include `ForceFeedbackActuator`, falling back to usages 0x30/0x31 (what the sibling `CyclicEffect` does).
  - **The TDX Force enumerates Y before X** (`Y Axis` offset 0 / usage 0x31, `X Axis` offset 4 / usage 0x30). Never assume position = X,Y: sort by usage for the UI and build direction vectors by usage (`EffectDirection.ToVector`).
  - **Direction convention: now verified** (see the firmware facts above) — the flip-180° assumption in `EffectDirection` plus the TDX Force's −90° device offset together give the right physical push on this stick (felt: forward/right/back/left/forward-right all correct). The two are entangled: `DirectInputDirectionIsSource` is only right *given* the device offset, so change them together, and re-test by feel with the log open, if a different FFB stick is ever added.
- Verified against a live running MSFS instance: the Editor's "Connect to Sim" toggle reaches `SimConnectionState.Connected` (real `OnRecvOpen` handshake, all 16 `AddToDataDefinition` calls + `RegisterDataDefineStruct`/`RequestDataOnSimObject` succeeding), and a `SimConnectNodeViewModel` wired directly to a (since-removed) placeholder output node showed real, continuously-updating `AIRSPEED INDICATED` values end-to-end through `GraphEvaluator` into the UI readout.

### Runtime app (icsmoi.Runtime)

`StatusWindowViewModel` drives the whole lightweight app: on window open it checks `RuntimeSettingsService` (a tiny `%LOCALAPPDATA%\icsmoi\runtime-settings.json` file) for a last-used profile path and auto-loads it — no user action needed on a normal (re)start. Loading a profile immediately starts `SimConnectTelemetryService` and `FfbEngineService` (unlike the Editor, Runtime has no manual "Connect"/"Start Engine" toggles — it's meant to just run).

**Effects safety gate**: loading a profile and running the engine only ever produces simulated magnitude readouts — `FfbEffectManager` is not created, and no device is acquired, until the user flips the status window's "Effects" `ToggleSwitch` on (default **off**). Flipping it off disposes `FfbEffectManager` immediately, tearing down every live effect. `FfbEngineService.HardwareOutputsUpdated` fires unconditionally every tick regardless of this toggle; `StatusWindowViewModel.OnHardwareOutputsUpdated` is what actually gates hardware access, by checking whether `_effectManager` (a `volatile` field) is non-null. Don't wire real effect creation anywhere that bypasses this toggle.

`_effectManager` is read on `FfbEngineService`'s timer thread and written on the UI thread (when the toggle flips) — it's `volatile` and captured into a local before use specifically to avoid a null-reference race. The dispose-while-in-flight race is **no longer** a limitation (it was once "accepted"): a tick that captured the manager just before the toggle disposed it used to call into the disposed DirectInput object, throw a `NullReferenceException` from `IDirectInput8.CreateDevice`, and have that reported as "Constant Force failed — Object reference not set…" over the "Effects: Disabled" text (reproduced in the real Runtime). Now `FfbEffectManager.SyncTick` is a no-op once disposed (under the same lock as `Dispose`), and on switch-off the Runtime nulls `_effectManager` first, unsubscribes `EffectFailed`, then disposes, and ignores a failure message that arrives after the switch was turned off. Failures are shown as `<ExceptionType>: <message>` and the full exception is appended to `%LOCALAPPDATA%\icsmoi\runtime-errors.log` (the status line only fits a fragment).

**Value ranges on the wire (all graph values are plain doubles).** *Joystick Input* outputs: axes/sliders **[-1, 1]** (each axis is forced to a ±1000 range and divided by 1000; centre = 0, a lever at its minimum = −1 — so it is *not* 0..1), buttons **0 or 1**, unassigned pins / no device / device unplugged **0**. *Hardware-output* inputs are normalized and converted by `FfbEffectManager.ToDirectInputUnits` (`value × 10000`, clamped to ±10000): Constant Force `Magnitude` **[-1, 1]** (the sign flips the push direction; beyond ±1 just saturates at full force); Condition `PositiveCoefficient`/`NegativeCoefficient`/`Offset` [-1, 1] and `DeadBand`/`Saturation` [0, 1]; Periodic `Magnitude`/`Offset` [-1, 1], `Period` seconds ≥ 0, `Phase` a cycle fraction that wraps; Ramp `StartMagnitude`/`EndMagnitude` [-1, 1], `Duration` seconds ≥ 0. `Gain` (0–10000) is a node setting, not a pin, and scales the whole effect. So wiring an axis straight into a Magnitude spans the full force range, and a multiplier like `× 5000` saturates almost immediately.

Profile loading (`Views/StatusWindow.axaml.cs`'s `OnLoadProfileClicked`) uses Avalonia's `IStorageProvider.OpenFilePickerAsync`, filtered to `*.icsmoi.json`, defaulting to the Documents folder (the Editor's save dialog can put profiles anywhere, so browse to wherever it was saved).

### Serialization

`ProfileSerializerService` reads/writes `FfbProfile` JSON at an arbitrary path (`SaveAsync(profile, path)`/`LoadAsync(path)`) via `System.Text.Json`. The Editor's 💾/📂 toolbar buttons open the OS file pickers (`Views/MainWindow.axaml.cs`'s `OnSaveClicked`/`OnLoadClicked` — the window owns the `StorageProvider`, then hands the chosen path to `MainWindowViewModel.SaveToPathAsync`/`LoadFromPathAsync`), so profiles can live anywhere. The Save dialog suggests `{ProfileName}.icsmoi.json`; `NormalizeProfilePath` forces the `.icsmoi.json` suffix (a bare name or plain `.json` is rewritten) because Runtime's picker only shows that pattern. The pickers reopen in the folder of `CurrentFilePath` (last loaded/saved), else Documents. Errors (wrong/corrupt/older file, e.g. one still containing a removed node type) are caught and shown in the toolbar's status field (in the error color) rather than crashing an `async void` handler. Polymorphism for node types is handled purely through `[JsonDerivedType]` attributes on `NodeViewModel` (no custom converter) — new node types must be registered there or they'll fail to round-trip. Connections are serialized as plain node/pin GUID pairs (`ConnectionViewModel`), not as live pin references; `MainWindowViewModel.LoadProfile` re-resolves GUIDs back into `PinViewModel` instances and rebuilds the live `Connections` collection on load.

### View binding

`ViewLocator` (in `icsmoi.Editor`) resolves views by naming convention: `Foo.ViewModels.BarViewModel` → `Foo.Views.BarView` (string replace on the full type name), falling back to a "Not Found" `TextBlock`. New view models need a matching view class following this convention to render.

### SimConnect telemetry (icsmoi.Core/Services/SimConnectTelemetryService.cs)

Vendored from the MSFS SDK — proprietary, not on NuGet: `lib/SimConnect/Microsoft.FlightSimulator.SimConnect.dll` (managed) + `lib/SimConnect/SimConnect.dll` (native), referenced only from `icsmoi.Core.csproj` via `HintPath`/`CopyToOutputDirectory`; both exe projects get the native DLL automatically through `ProjectReference` content propagation. Sourced from the user's sibling `TDX-Air-Mechanics` project, which already has a working SimConnect integration for MSFS.

`SimConnectTelemetryService` runs on its own `TaskCreationOptions.LongRunning` task: constructs `SimConnect` with a real native window handle (required by its constructor) but never pumps Win32 messages for it — it polls `ReceiveMessage()` manually in a `Thread.Sleep(16)` loop instead, exactly like TDX's own `SimConnectService.cs`. Two deltas from TDX: it auto-retries the connection on a timer (`Disconnected → Connecting → Connected` state machine, retried every 5s) instead of requiring a manual "Connect" click, and it requests `SIMCONNECT_PERIOD.VISUAL_FRAME` instead of TDX's `SECOND` for lower-latency FFB-relevant updates. **Known quirk**: constructing `SimConnect` when the sim isn't running doesn't always throw — it can also silently never raise `OnRecvOpen`. A `ConnectTimeout` (5s) treats "still Connecting after N seconds" the same as a thrown exception and retries, rather than getting stuck.

Telemetry lands directly in `FfbEngineService.SimData`, keyed by SimConnect variable name exactly as `SimConnectNodeViewModel.VariableName`/`SimVariableCatalog` use it — no intermediate DTO. `SimVariableCatalog.KnownVariables`' order is load-bearing: it must match `SimConnectTelemetryService`'s internal `TelemetryData` struct field order exactly, since SimConnect maps registered variables to struct fields positionally, not by name (the struct uses a `fixed double Values[SimVariableCatalog.Count]` buffer specifically to make this positional mapping explicit rather than relying on reflection's unordered `GetFields()`).

### Joystick input (icsmoi.Core/Services/DirectInput/JoystickDevices.cs, JoystickInputService.cs)

Read-only and safe in both apps: devices are opened **non-exclusive, background, never with an effect** (unlike `FfbDeviceManager`), via `IDirectInputDevice8.SetDataFormat<RawJoystickState>()` + `GetCurrentJoystickState()`. Every axis is forced to a symmetric ±1000 range (`Properties.Range`, which must be set *before* `Acquire`) and normalized to [-1, 1], so devices with different driver ranges behave alike. `JoystickDevices.EnumerateDevices()` lists every attached game controller (feeds `MainWindowViewModel.AvailableJoysticks`).

`JoystickInputService` polls (own `LongRunning` thread, ~15 ms) the devices named by `SetTrackedDevices` and publishes **all 8 axes and 128 buttons** of each into `FfbEngineService.SimData` — the same dictionary SimConnect telemetry uses, so `GraphEvaluator`'s signature didn't change — under `JoystickInputKey.For(device, kind, index)` keys (`joy:<guid>:a3` / `:b2`; the poller and `GraphEvaluator.EvalJoystick` both build keys through that helper). Publishing everything means adding/re-binding rows never needs the tracked set refreshed — only the *device* set does. The poll thread must never touch the (UI-thread) node graph, so hosts derive that set themselves: the Runtime once per profile load (`StartTelemetryAndEngine`); the Editor starts the service with the engine and re-derives the set every 500 ms from a `DispatcherTimer` (catches node add/delete, device changes, profile load). A device that can't be opened is retried every 2 s; a device that disappears has its keys zeroed so no value sticks.

**Capture** (assigning a row): click a row's field → `MainWindowViewModel.BeginJoystickCaptureCommand` → `JoystickDevices.Capture` (own short-lived device handle, run on `Task.Run`, 15 s timeout, click again to cancel) returns the first input actuated; the decision logic is the pure `JoystickCaptureDetector` (button = released→pressed edge, one already held at start is ignored until re-pressed; axis = moved ≥ 0.25 of its −1..1 span from where it started; button beats axis; biggest axis mover wins). **Gotcha**: the first state read after `Acquire` is stale (all zeros), which made every held button look freshly pressed and a capture return instantly — `Capture` reads, waits 80 ms, then reads again for the baseline. Hats (POV) are not supported.

Rows are pins, so add/remove is a graph edit: `AddJoystickInputCommand`/`RemoveJoystickInputCommand` live on `MainWindowViewModel` (removal calls `DisconnectConnector(pin)` first, honoring the dual-collection rule) and the row buttons reach them through reflection bindings (`x:CompileBindings="False"` on those two buttons only). After an add/remove `MainWindowViewModel.PinLayoutChanged` makes `MainWindow` call `Connector.UpdateAnchor()` on every connector at `Background` priority: pins below a removed row move up but the node's *size* may not change, and NodifyM only refreshes anchors on move/resize, so wires would otherwise keep pointing at the old spots.

**Engine thread safety**: Joystick rows are the first pins that change after the node exists, and `FfbEngineService.Tick` enumerates `node.Outputs` on the timer thread — so `Tick` now catches `InvalidOperationException`/`ArgumentException`/`IndexOutOfRangeException` from `Evaluate` and skips that tick (an exception escaping a `Timer` callback kills the process). Note the Editor still never calls `RefreshSnapshot` after `Engine.Start`, so nodes/links added *while the engine runs* aren't evaluated until it is restarted (pre-existing); edits to existing nodes' pins/values are seen live.

**`[JsonIgnore]` + `[ObservableProperty]`**: a plain `[JsonIgnore]` on the field never reaches the generated property — use `[property: JsonIgnore]` (as `JoystickPinViewModel.IsListening` does). The older runtime-only properties (`IsSelected`, the `Last*` readouts) use the plain form and **are in fact written to saved profiles** (verified); harmless but untidy, not yet fixed.

The Editor's "Connect to Sim" toolbar toggle (`MainWindowViewModel.ToggleSimConnectionCommand`) is test-run telemetry only, per the Editor/Runtime hardware boundary above — it feeds live values into `LastMagnitude`-style readouts, nothing more.

### Visual design system (icsmoi.Shared.Ui/Styles/Tokens.axaml)

A single dark "Afterburner" palette (graphite surfaces, afterburner-orange `#FF5A1F` accent for "force", steel blue for "air"), not an OS-theme-following one: both apps set `RequestedThemeVariant="Dark"` explicitly and there is no light-theme variant. `Tokens.axaml` defines two families of resources, merged into both `App.axaml`s:

Used throughout `MainWindow.axaml` and `StatusWindow.axaml` instead of hardcoded hex — if you add new chrome, use these rather than introducing another hex literal.
- **Per-node-category accent tokens** — `Icsmoi.Category.Input` (steel blue) / `MathLogic` (teal) / `Shaping` (gold) / `HardwareOutput` (afterburner orange, same as `Accent` — force is the brand color). Every node `DataTemplate` in `Views/NodeTemplates.axaml` sets `HeaderBrush="{DynamicResource Icsmoi.Category.X}"` on its `controls:Node` (replacing the old hand-rolled 3px body stripe, which couldn't reach the rounded edges); header text is dark (`Icsmoi.Background`) for contrast. Keep new node types' header tint consistent with their category. Selection ring is near-white (`Icsmoi.Text`, not Accent, which would be ambiguous with the HardwareOutput orange); hover ring is the Input steel blue.
- **Shape tokens** — `Icsmoi.PillRadius` (999), `NodeRadius` (12), `ChipRadius` (8), plus `NodeHeaderRadius`/`NodeFooterRadius` (`10,10,0,0` / `0,0,10,10` = `NodeRadius` minus the node's 2px border). The header/footer fills must use these inner radii explicitly — relying on the outer border's `ClipToBounds` alone left the header's corners visibly tighter than, and overshooting, the selection ring.

**Shape/control styles.** `icsmoi.Shared.Ui/Styles/Controls.axaml` (a `Styles` file, included after `<FluentTheme />` in both `App.axaml`s) makes every exact-type `Button` a pill (`CornerRadius` = `PillRadius` — Fluent's Button template binds its `ContentPresenter` to `CornerRadius`, so a large radius clamps to a stadium shape). If pills read badly somewhere (long stacked labels such as the sidebar palette), scope down with an opt-in class rather than reverting.

**Canvas grid color.** NodifyM's `LargeGridLine` control does *not* read the `GridLinesColor` resource (only the minimap border does): it draws with its own `Brush` property (default `Gainsboro`) at 0.5px thickness, which anti-aliases to ~25% coverage. So overriding `GridLinesColor` alone does nothing to the visible grid — `NodeStyles.axaml` styles `controls|LargeGridLine`'s `Brush` from `Icsmoi.GridLines` (`Tokens.axaml`). The visible line is roughly background + 25% of (brush − background), so that brush is deliberately ~4× brighter than the line you see; tune the single `Icsmoi.GridLinesColor` value to adjust.

**Logo / app icon.** `icsmoi.Shared.Ui/Styles/Logo.axaml` (merged into both `App.axaml`s) defines two `ContentControl` themes: `Icsmoi.Wordmark` — the lowercase "icsmoi" in very round, heavy, monoline letters (letters `Icsmoi.Text`; the two round letters, "c" and "o", `Icsmoi.Accent`), drawn as stroke-only centrelines on a ~92×29 canvas (stroke 4.5, x-height 13, no font dependency; thick strokes eat counters, so widen letters rather than thinning the stroke). **Letter spacing is optical, not geometric**: equal bounding-box gaps looked uneven (the open `c` next to `s` read far looser), so each pair was measured as the mean silhouette-to-silhouette space over the x-height band (depth capped at 25% of x-height) and shifted to a common ~5.0-unit gap — the resulting box-to-box gaps differ on purpose (documented in `Logo.axaml`'s header comment) — and `Icsmoi.Monogram` (dark disc + orange ring + light `i` stem + orange dot on a 64×64 grid). The wordmark sits at the far left of the Editor toolbar (before "Profile:") and heads the Runtime status window next to a muted "Runtime" caption. The **app icon** `icsmoi.Shared.Ui/Assets/icsmoi.ico` (16–256px, PNG-compressed) is the monogram, generated by `tools/GenerateAppIcon.ps1` (`powershell -ExecutionPolicy Bypass -File tools/GenerateAppIcon.ps1`) with `System.Drawing` — its primitives duplicate the `Icsmoi.Monogram` theme, so keep the two in sync when either changes. **Axis dropdown & direction dial (hardware-output nodes).** The shared settings block's *Axis* is a `ComboBox` of `AxisChoice`s — "All axes" plus the selected device's force axes — kept in `HardwareOutputNodeViewModel.AxisChoices` (runtime-only) by `MainWindowViewModel.UpdateAxisChoices`, which runs when a node is added/loaded (via `Nodes.CollectionChanged`), when its device changes, and on `RefreshDevices`. **It binds `SelectedItem` to `SelectedAxis`, not `SelectedValue`**: `SelectedValue` lost any non-zero selection when the items arrived after the binding (exactly the profile-load order) and left the dropdown blank; `SelectedAxis` is re-notified *after* `AxisChoices` via `[NotifyPropertyChangedFor]` so the dropdown has its items first. When `ShowsDirection` (All axes + a direction-capable effect) the block also shows `Views/DirectionDialControl.cs` and a degrees `NumericUpDown` bound to the same `DirectionDegrees`. The dial is custom-rendered from the design tokens (graphite face with a radial lift, fine 15° ticks with stronger cardinals/diagonals, a forward triangle, an accent fan + spoke to a glowing handle dot on a track ring); click/drag anywhere sets the angle in whole degrees, Shift snaps to 15°, and it marks its pointer events handled so the node isn't dragged.

`FfbEffectManager` applies it: a chosen axis → that one axis with direction `[0]` (the magnitude's sign is the direction, as before); All → every force axis with a Cartesian direction vector from the dial (a device with one force axis just uses it); Condition → one identical `Condition` per axis, no direction. Gain and direction changes are applied in place (`EffectParameterFlags.Gain`/`Direction`); a change of axis selection or effect type (`ConditionKind`/`Waveform`) rebuilds the effect (neither can be changed on a live effect) — before this, only the type-specific parameters were ever updated, so gain edits were silently ignored. Any exception creating/updating a node's effect is caught per node (`EffectFailed` event → Runtime shows it in the Effects status line), the effect is torn down and retried after 3 s: an exception escaping the engine's `Timer` callback would kill the process, and the Effects path had no such guard.

**TDX Force firmware facts that shape the effect code (read from `C:\Users\crist\Documents\HB\TDX_Force`, STM32 firmware, `Core/Src/app_effect.c`, `app_ffb.c`, `USBX/App/ux_device_customhid.c`).** Report IDs: `0x01` Set Effect, `0x05` Set Constant Force, `0x0A` Effect Operation, `0x0C` Device Control, `0x0D` Gain, `0x10` (16) **Create New Effect** (a `SET_FEATURE`; first byte = effect type), `0x11` (17) **Block Load** (a `GET_REPORT` returning the new slot index), `0x12` (18) Pool. Three behaviours matter:
  - **Slots have states, and most reports are ignored unless the slot is `DEFINED`.** `create_new_effect` (report 16) marks a slot `RESERVED`; only **Set Effect** turns it `DEFINED`; `set_constant_force_report`, `set_periodic_report` and `set_ramp_report` store their values **only if `DEFINED`** (`set_condition_report` accepts anything non-idle — which is why springs/dampers worked from the start). DirectInput's create-time download sends the type-specific report *before* Set Effect, so the initial magnitude of a constant/periodic/ramp effect is silently dropped. Fix (`FfbEffectManager`): right after `CreateEffect`, call `SetParameters(TypeSpecific | Direction | Start)` once more — the working app's log shows exactly `Set const force, Set eff, Set const force, Set eff, Start`. Without it a steady graph value never re-sent the magnitude, so the effect played at 0 forever.
  - **Device Reset wipes every slot, and it races Create.** `Device_Reset` calls `reset_effects()` (every slot → IDLE). Output reports (Reset, gain, Set Effect…) go through a queue to a slow, UART-logging thread, while report 16/17 are control transfers handled immediately. DirectInput does its own init (pool report, reset, gain) lazily *inside the first `CreateEffect`* — so the queued Reset ran **after** the effect was created and wiped it (visible in the log as `SET_FEATURE 16 / Block Load` printing *before* `[HID] 12 - Resetting device`). No error, no force. Fix (`FfbDeviceManager.AcquireDevice`, copied from the working sibling `MechanicService`): set `AutoCenter=false` and `ForceFeedbackGain=10000`, `Acquire`, then `SendForceFeedbackCommand(StopAll)` + `(Reset)`, then wait 500 ms so the stick drains its queue *before* anything is created. The log then reads init → gap → create, like the working app's.
  - **Constant-force direction is a math-convention angle.** `FFB_ComputeConstantForce` applies `roll = −F·cos(dir)`, `pitch = −F·sin(dir)` (`dir` in hundredths of a degree, roll = X axis, pitch = Y). DirectInput's polar direction (what our vector becomes: `dir = atan2(vx, −vy)`) is clockwise from north, so on this stick the push comes out **90° clockwise of where asked** — an earlier "pitch is inverted" report (46° came out right-and-back instead of forward-right) was really this rotation, not a Y flip. `FfbDeviceManager.GetDirectionOffsetDegrees` returns −90 for a device named "TDX Force" and `EffectDirection.ToVector` adds it, so the firmware sees `dir = dial + 90°` (verified in the log: dial 0/90/180/270 → dir 9000/18000/27000/0). **Verified by feel on the real stick** (five 85% pushes through the real manager, user-confirmed): dial 0°/90°/180°/270°/46° pushed forward/right/back/left/forward-right, i.e. roll+ = right and pitch+ = back as inferred. The old per-node "Invert pitch" checkbox was a misdiagnosis and has been removed.
**Reading the stick's log (the debugging tool that broke this open).** The TDX Force's firmware prints its HID/PID traffic on the ST-Link virtual COM port — **COM7 at 115200 8N1** (`System.IO.Ports.SerialPort`; it opens fine even with Termite running). Lines like `[HID] 5 - Set const force 1, magnitude=32766` (magnitude scale: DirectInput ±10000 → ±32766), `[HID] 1 - Set eff (1): … dir=22599` (direction in hundredths of a degree: 22599 = 226°), `[HID] 10 - Eff op 1: operation=1` (Start) / `operation=3` (Stop), `Free block 1`, `Resetting device`; the `CAN Tx FIFO full, dropping message` bursts at effect creation/reset are normal. Capture it in a harness alongside your calls and compare against the working app's log — that comparison, not "does it throw", is the only way to know the stick got what you meant (a harness that produces no errors and no force is easy to write). `x_dir`/`y_dir` stay 0. Use only small forces while testing; a person may be holding the stick.

**Effect update cost (measured on the real TDX Force) — why the engine tick is non-reentrant.** Updates use the working app's pattern, `TypeSpecificParameters | Start | Direction`, which makes DirectInput send `Set const force` → `Set eff` → `Eff op start` each time (`TypeSpecific | Start` alone omits `Set eff`; adding `Direction`, `Gain` or `Duration` includes it — checked against the live log). Once the slot is `DEFINED` a bare magnitude update would also be stored, so the per-update `Set eff` is belt-and-braces (and is what carries a changed direction/gain). **The bug that made all of this "work" with no force was at creation, not in updates — see the firmware facts above; several rounds of "tests" that only checked for exceptions proved nothing.** (`EffectParameterFlags.All` throws `0x800704DF` here — don't use it. `x_ena=0, y_ena=0, dir_ena=1` in the `Set eff` line is normal for this firmware.) Strength: forces below roughly 50% were not perceptible on this stick in testing. The cost of `Start`: a `SetParameters` call *with* it takes a fixed ~16 ms USB round trip (≈63/s max), ~0.02 ms without. `System.Threading.Timer` fires every period regardless of whether the previous callback has returned, and the engine's period is 10 ms — so with the old per-tick `Start` update the ticks piled up (median tick 480 ms, **33 concurrent ticks**), raced each other (each saw "no effect yet" and called `CreateEffect`: **13 effects in 5 s instead of 1**, the orphans left playing and their forces adding up) and hammered the device. Two layers now prevent it: `FfbEngineService.Tick` skips when a tick is already running (`_tickRunning`), and `FfbEffectManager` serializes `SyncTick`/`Dispose` with a lock and only talks to the device when the DirectInput-unit values (or gain/direction) changed — so a steady graph value costs nothing and a changing one is limited to the device's ~60 updates/s by the tick skipping rather than queueing. Because every update restarts the effect (see above), a *periodic* effect restarts its cycle whenever its parameters change; with unchanged parameters it is left alone and oscillates normally. A **Ramp** additionally sets `Duration` on update. `FfbEffectManager.EffectsCreated` exists so a test can assert "one effect per node" — the check that caught this.

**Hardware-output node layout & pin value fields.** The four hardware-output templates put each input pin in a row from `ValueInputPinTemplate` (`Views/NodeTemplates.axaml`): a `NodeInput` plus a compact `NumericUpDown` (`Classes="field"`, styled in `Styles/NodeStyles.axaml` — Fluent draws a `NumericUpDown`'s border on an inner `ButtonSpinner#PART_Spinner` whose `MinHeight` is theme-set, so compact sizing must lower *that part's* `MinHeight`; forcing `Height` on the `NumericUpDown` itself clips the spinner and loses the top/bottom border and rounded corners) bound to `PinViewModel.Value`, with `IsVisible="{Binding !IsConnected}"` — so the field is shown only while no link feeds the pin and reappears (with its stored value) when the link is removed. Three deliberate choices, each learned from NodifyM's `Connector` source: (1) the field sits *beside* the `NodeInput`, not in its `Header` — `Connector.OnPointerPressed` captures the pointer and starts a connection drag for any press that reaches it; (2) the row has a fixed `MinHeight` so showing/hiding the field never moves the pin — NodifyM only recomputes pin anchors on node move/resize, so a row that shrank inside a taller node would leave stale wire endpoints; (3) title columns use `SharedSizeGroup="PinTitle"` with `Grid.IsSharedSizeScope="True"` set on the input `ItemsControl` in the copied `Node` template, so fields line up across rows. The device/axis/gain block is a single shared `HardwareOutputSettingsTemplate` (`DataType` = `HardwareOutputNodeViewModel`) hosted via a `ContentControl` in each of the four node templates, followed by that node's own readout chip.
**Joystick Input node template.** Input-category header; body = joystick `ComboBox` + a small "+ Add input" button; the rows are the *output* pin template `JoystickOutputPinTemplate` (`[click-to-capture field] [✕] ○`, fixed `MinHeight` like the input rows).
